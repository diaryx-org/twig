# Twig — notes for an agent

Conventions that are enforced by tooling, or that a reviewer will send a change
back for, and that are not discoverable from the code you are editing. Read this
before writing a commit.

Nothing here is a substitute for [DESIGN.md](/docs/DESIGN.md), which is where the
vocabulary Twig's source comments use is defined.

## A behavioural change is recorded on its commit

If a change alters **what an existing call returns** — a span whose extent
moves, a node that reparents, a field that starts reporting `NONE`, an error
code that stops being returned — say so in a `Behavioural-change:` trailer on
the commit that causes it:

```
fix(markdown): a block quote's span covers its own trailing marker lines

<the body: why, and how it works>

Behavioural-change: A Markdown `block_quote`'s span now covers its own
  trailing marker lines. `"> a\n>\n> \n"` reported `0..3` and now reports
  `0..8`. `content_span` is unchanged.
```

`cliff.toml` collects those trailers into CHANGELOG.md's **Behavioural
changes** section and into the GitHub release body. Nobody writes that section
by hand, and a note that is not on its commit does not exist.

The test for whether a change needs one: *would a caller who upgrades without
editing a line of their own code observe a difference?* If yes, it needs a
trailer — even when the change is a bug fix, and even when the old behaviour
was plainly wrong. This is the class that compiles clean and fails at runtime,
which is why it gets its own section rather than a line in the body.

One trailer per observable difference; a commit may carry several. Most commits
carry none. Continuation lines are indented two spaces and fold into one
paragraph. Write the value for someone deciding whether to upgrade — what used
to happen, what happens now — not for a reviewer reading the diff; the body
above it is for that.

The full rules, including what is still written by hand, are in
[CHANGELOG.md](/docs/CHANGELOG.md)'s own header sections.

## Do not hand-edit the generated region

Everything between the `git-cliff:begin` and `git-cliff:end` markers in
CHANGELOG.md is regenerated by `scripts/changelog.sh --write` and your edits
there are overwritten. `scripts/changelog.sh --check` fails if the region is
stale.

The only prose written by hand is a release **intro**, below the end marker,
for a release that wants a narrative rather than a list. Most want none.

Cutting a release is a command, not a checklist: `zig build release -- <minor|…>`
bumps, verifies, regenerates and cuts the region, commits, and tags — and stops
before the push. See [RELEASING.md](/docs/RELEASING.md).

## Commit subjects

Conventional commits, with `add(scope):` as Twig's spelling of `feat(scope):`
(both are accepted). The scope names the surface that moved — `add(editor)`,
`fix(djot)`, `fix(markdown)` — and is what the changelog bolds.

Keep the subject on **one line**. A subject that wraps fails
`git-conventional` parsing, which costs it its scope and its grouping, and
leaves the raw `type(scope):` prefix visible in the changelog. `44843ea` is
what that looks like.

`docs:`, `chore:`, `test:`, `ci:`, `build:` and `style:` are skipped by the
changelog entirely. Anything the parser does not recognise lands in a visible
"Uncategorised — triage before release" bucket rather than being dropped.

## Tests

`zig build test` runs everything: the module, exe, C-ABI and bench test
artifacts, plus — on any non-wasm target — a C header test that compiles
`bindings/c/include/twig.h` against the built library.

Span changes are the ones worth being careful with, and the way to check one is
to **slice the source with the resulting span and assert on the bytes** —
`try testing.expectEqualStrings("> a\n>\n> ", src[sp.start..sp.end])`. A span
bug is usually invisible in the HTML, so a rendering assertion will not catch
it. `src/languages/markdown/block.zig`'s `span:`-prefixed tests are the pattern.

For the Rust bindings, `cargo test` links a prebuilt `libtwig.a` unless
`TWIG_SYS_FORCE_SOURCE=1` is set. Without it you are testing the published Zig,
not your working tree — so any change to `src/` needs that variable, or it will
pass for the wrong reason. `zig build check` runs both suites the way CI does,
with that variable set, and is the gate `zig build release` runs before it
commits anything.
